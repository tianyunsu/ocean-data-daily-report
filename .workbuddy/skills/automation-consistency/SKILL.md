# 手动 / 定时自动化执行一致性

## 何时使用

- 用户说"手动执行要和自动执行一致""手动跑也记得写记忆/经验""不管手动频率如何都要一致"
- 发现定时任务的记忆文件出现断层：某几天（通常是手动执行的日子）没有 `.workbuddy/memory/YYYY-MM-DD.md`、
  没有写入 `MEMORY.md` 去重基准、或自动化 `automations/<id>/memory.md` 缺记录
- 发现 `daily_reports/`（或类似的"源文件"目录）在手动执行日缺失对应文件，而 `posts/`/`dist/`（部署目录）却有

## 核心问题模型

定时自动化与手动执行本质是**同一个任务的两个入口**。记忆断层几乎都源于：

1. **双源定义**：自动化 prompt 内联了完整流程细节，skill 也内联了细节 → 两处各自演进，手动入口只走了"核心产出"
   而漏掉"记忆写入"步骤（因为当时 skill 还没强制该步骤，或手动执行根本没加载 skill）。
2. **手动入口未加载权威源**：手动触发时直接跑脚本/写文件，跳过了 skill 要求的"阶段六记忆写入"。
3. **缺少一致性铁律**：没有明文规定"手动 ≠ 简化"，导致手动执行者主观省略步骤。

## 修复架构：单一权威源 + 纯委托

```
            ┌─────────────────────────────────┐
            │   ocean-daily-report (skill)     │  ← 唯一权威源
            │   6 阶段 + 阶段六记忆写入 + 铁律   │
            └─────────────────────────────────┘
               ▲ 加载             ▲ 加载
        ┌──────┴──────┐    ┌──────┴──────┐
   手动触发（对话）   自动化 prompt（纯委托，不重复定义细节）
        └─────────────┘    └─────────────┘
        二者共用同一流程与阶段六 → 记忆写入完全一致
```

**关键原则**：流程细节只存在于 skill 一处。自动化 prompt 是"薄委托层"，手动入口也是"加载 skill"。
任何流程调整**先改 skill**，两入口自动继承，从机制上杜绝漂移。

## 标准执行步骤

### 步骤 1 — 诊断断层（先量化差异）

同时列出手动执行日与自动执行日的产出物，逐类对比：

| 工件类型 | 手动执行日 | 自动执行日 | 判定 |
|---------|-----------|-----------|------|
| 部署目录文件（如 `posts/YYYY-MM-DD.html`） | 有 | 有 | 通常一致 |
| 源文件目录（如 `daily_reports/海洋AI简报_*.html`） | ❌ 缺 | ✅ 有 | 手动漏写 |
| `.workbuddy/memory/YYYY-MM-DD.md` 每日日志 | ❌ 缺 | ✅ 有 | 手动漏写 |
| `MEMORY.md` 去重基准更新 | ❌ 缺 | ✅ 有 | 手动漏写 |
| `automations/<id>/memory.md` 执行摘要 | ❌ 缺 | ✅ 有 | 手动漏写 |

用 Bash 枚举：`ls .workbuddy/memory/2026-07-*.md`、`ls daily_reports/ | grep 2026-07`、
`ls posts/ | grep 2026-07` 交叉比对，定位"有部署但无记忆"的断点日期。

### 步骤 2 — 强化 skill 的"一致性铁律"与"阶段六"

在 skill 顶部加/补一段明文（如 ocean-daily-report 的「重要：本技能为手动/自动共享指令源（权威唯一来源）」）：

> 手动触发 ≠ 简化执行。手动触发的任务必须产出与定时自动运行**完全相同**的工件与记忆文件，
> 包括源文件、部署文件、每日日志、去重基准更新。任何"跳过某步"都会造成记忆断层，必须避免。

把"记忆写入"定义为独立阶段（如「阶段六：记忆写入（不可跳过，手动与自动完全一致）」），明确列出
必须写入的全部文件清单：
1. `$WORKSPACE/.workbuddy/memory/YYYY-MM-DD.md` 每日日志（追加，不覆盖）
2. `$WORKSPACE/.workbuddy/memory/MEMORY.md` 去重基准追加本期核心条目
3. 经验沉淀（如发现 skill/MEMORY.md 有遗漏规则立即更新）
4. （可选推荐）`$WORKSPACE/.workbuddy/automations/<id>/memory.md` 追加高层面执行摘要，使手动/自动有统一历史视图

### 步骤 3 — 把自动化 prompt 改为对 skill 的纯委托

用 `automation_update` 模式 `update` 改写该自动化 prompt：去掉内联的阶段细节，改为：

```
你是 <任务名> 的自动化执行者。本自动化与"手动触发"共用完全相同的流程、记忆文件与经验基准。

## 执行方式（唯一权威源）
1. 立即用 Skill 工具加载 `<skill_name>` —— 它是本次执行的唯一权威指令源。
2. 严格按 skill 定义的阶段顺序执行，不得跳过任何阶段（含记忆写入阶段）。
3. 运行日期 = 当天日期。

## 关键约束
- workspace / 仓库 / 用户 等固定参数

## 铁律
- 不要在本 prompt 内重复定义流程细节——以 skill 为准。任何流程调整先改 skill，本 prompt 自动继承。
- 记忆写入阶段必须执行，且写入文件与手动执行完全一致。
```

### 步骤 4 — 补写历史断层的记忆文件（消除已发生的 gap）

对步骤 1 发现的"有部署但无记忆"的日期，从部署目录的产出物还原内容并补写：

1. 从 `posts/YYYY-MM-DD.html`（或对应部署文件）提取条目标题/摘要：
   - 结构已知时用 Grep；结构不确定时用 Python `re.findall(r'class="item-title">(.*?)</div>', txt, re.S)` 提取后清洗。
2. 用 `git log --grep="YYYY-MM-DD"` 取提交信息辅助还原亮点。
3. 写 `.workbuddy/memory/YYYY-MM-DD.md`，注明"本次为手动执行，原未写本文件，<日期> 质检补写以消除断层"。
4. 同时在 `automations/<id>/memory.md` 顶部追加改造说明（可选）。

> 补写的目的是让未来去重检索与回顾能看到完整历史，避免"记忆从某天断掉"。

### 步骤 5 — 验证一致性

再次枚举三类文件，确认目标日期现在三处齐全：

```
ls .workbuddy/memory/2026-07-*.md   # 应含所有执行日
ls daily_reports/ | grep 2026-07     # 手动日也应出现源文件（下次执行即补齐）
ls posts/ | grep 2026-07             # 部署本就齐全
```

并在今日 `.workbuddy/memory/YYYY-MM-DD.md` 追加"一致性改造"记录，说明改动点与机制保证。

## 常见陷阱

1. **只补文件不修机制**：仅补写 history 日志而不改 skill/prompt，下次手动仍会漏写。必须"补历史 + 修机制"双管齐下。
2. **自动化 prompt 仍内联细节**：若 prompt 保留完整流程，它与 skill 迟早漂移。务必改成纯委托。
3. **把自动化 memory.md 当唯一真相**：自动化 memory.md 是定时任务自己的簿记，手动执行是否写入它应是"可选推荐"，
   真正的强制一致性锚点是 `.workbuddy/memory/YYYY-MM-DD.md` 与 `MEMORY.md` 去重基准。
4. **跨平台编码**：Windows 下 git push 须在 Bash 且 `dangerouslyDisableSandbox: true`；中文内容一律用 Write 工具写文件，禁止 bash heredoc。

## 扩展：跨机器一致性（多台电脑执行同一任务）

当用户在多台电脑上手动触发同一任务时，"一致"的维度从"手动 vs 自动"扩展为"机器 A vs 机器 B"。核心是把三类资产分别归位：

| 资产 | 天然位置 | 跨机器方案 |
|------|----------|-----------|
| 记忆文件（日志、去重基准、执行摘要） | 工作区 `.workbuddy/memory`、`.workbuddy/automations` | **纳入 git 版本控制**，随仓库 clone/pull 同步 |
| skill（权威指令源） | 用户级 `~/.workbuddy/skills/` | **不随仓库**，需在仓库内存副本 + 同步脚本 |
| 执行脚本、历史产出 | 工作区 | 随仓库同步 |

**标准做法**：

1. 确认 `.workbuddy/` 是否已被 git 跟踪：`git ls-files .workbuddy/ | wc -l`。未跟踪则先 `git add` 纳入（注意先检查有无密钥、token）。
2. 在仓库内建 `.workbuddy/skills/`，把用户级 skill 复制进去。
3. 写一个同步脚本（如 `sync_skills.py`），提供三种模式：
   - `install`：仓库 → 用户目录（新机器配置 / 每次 pull 后）
   - `collect`：用户目录 → 仓库（本机改了 skill 后回收，准备 push）
   - `status`：MD5 比对差异，只读不改
4. 在 skill 的铁律段增加**跨机器铁律**：
   - 执行前 `git pull` + `sync install`（**不拉最新记忆 = 去重基准过期 = 必然重复产出**）
   - 执行后必须 `git push` 推送记忆
   - 禁止两台机器同一天并行执行（git 冲突 + 内容重复）
   - 非主力机改 skill 须 `collect` 回收后 push，否则改动丢失
5. 写一份 `SETUP_NEW_MACHINE.md` 放仓库根目录：资产位置表 → 首次配置步骤 → 每次执行标准动作 → 常见问题。

**跨机器特有陷阱**：

- 记忆冲突时不要直接取一侧覆盖——每日日志按日期天然不冲突，但 `MEMORY.md` 去重基准必须**手动合并两侧条目**。
- 同步脚本用 Python 而非 shell，避免 Windows/macOS 差异。
- 别把 skill 做成 symlink 跨机器共享，路径在不同机器上不一致，复制才可靠。

## 适用边界

- 适用于"同一任务有定时自动化 + 用户也会手动触发"的场景（日报、周报、定期抓取、定期分析等）。
- 跨机器扩展章节适用于"同一任务在多台电脑上执行"的场景，与是否有定时自动化无关。
- 若任务**只有**定时自动化、从不被手动触发，则无需本 skill，阶段六记忆写入本就是自动化的固有步骤。
